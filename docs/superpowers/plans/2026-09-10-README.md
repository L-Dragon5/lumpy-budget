## Global constraints

Copied verbatim from `CLAUDE.md` and `README.md`; every task inherits them.

- **Money is always an integer number of cents.** No floats, no `DECIMAL`.
- **Dates are always `YYYY-MM-DD` strings.** No `Date` object crosses the DB or
  HTTP boundary. A raw `tx.unsafe` SELECT does **not** go through `coerce()`, so
  a hand-written statement must say `DATE_FORMAT(col,'%Y-%m-%d')` itself.
- **Query params use `.optional()`, never `.default()`.** A zod default lands in
  the output type, which Eden hands the client, making an optional param
  required. Default inside the handler.
- **Validation failures are 422 in Elysia's shape, not 400.**
- **A column lives in four places, in this order:** a numbered migration,
  `services/db/src/tables.ts`, `contracts/types.ts`, then the scenario
  expectations. Miss one and reads silently drop it.
- **Migrations are forward-only.** Start at 013. Do not reuse a number below 011.
- **`bun run check`** is typecheck + `bun test` + `bun run scenarios`, and is
  exactly what the pre-commit hook runs. It must be green at every commit.
- `bun test` needs MySQL running; `services/api/test/*` hits a real
  `lumpy_budget_test` database via `TEST_DATABASE_URL`.
- The hook is not installed by cloning: `git config core.hooksPath .githooks`.
- **Never skip a hook with `--no-verify`.**

## Migration numbers are claimed up front

013 is income-actuals. 014 is transaction-splits. Two sessions must not both
reach for 013. If a plan is dropped, its number stays burned rather than being
recycled: a number that once meant something else is a number an existing
`_migrations` table already believes it has run.

## The one real collision

`transaction-splits` hides split parents from every expense read. Two queries
written by other plans have to learn about that, and each is a numbered step
inside the splits plan itself (Task 7), not a change the other plans make:

- `store.expensesBetween` and the `/expenses` list route (splits' own work).
- `store.cardBalances` from the card-balance plan, whose `SUM(amount_cents)`
  would count a split parent and its children both.

**Merge order:** if both land, merge `card-balance` first, then
`transaction-splits`, whose Task 7 Step 4 applies the predicate to the card
query. If `card-balance` is not merged, splits' Task 7 Step 4 is a no-op and
says so.

`income-actuals` and `shadowed-rules` collide with nothing.

## Recommended order if run serially

1. `income-actuals` — it fixes a live undercount (see its Task 2) and changes
   `bucketOf`, which the other plans read.
2. `shadowed-rules` — pure, no schema, no risk.
3. `card-balance` — read-only report.
4. `transaction-splits` — the only one that writes new rows.
